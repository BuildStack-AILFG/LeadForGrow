## 2026-09-24 — Email broadcasts: real signature, rich WYSIWYG body, email-only CSV, honest email stats
Branch: main
Files:
- `models/automation/Broadcast.js` (added `content.emailAccountId`, `content.signatureId`, `content.bodyHtml`)
- `lib/broadcasts/engine.js` (new `resolveEmailSender` — builds the selected mailbox's transporter + resolves its signature ONCE per broadcast; new `sendBroadcastEmailViaAccount` — sends from that mailbox's SMTP with the signature + compliant unsubscribe footer + inbox provenance `origin='broadcast'`; email loop uses the account path when a mailbox is chosen, legacy `sendCustomerEmail` fallback otherwise; uses `content.bodyHtml` verbatim as the HTML part when present, else escapes the plain `body`)
- `lib/integrations/email.js` (exported `buildUnsubscribeUrl` so the engine reuses the exact same unsubscribe footer)
- `app/api/automation/broadcasts/preview-message/route.js` (resolves the same `account.resolveSignatureHtml(signatureId)` and applies vars to `bodyHtml` — preview and send never diverge)
- `app/api/automation/broadcasts/import-csv/route.js` (channel-aware: email campaigns require an EMAIL column and dedupe/upsert by email, phone optional; WhatsApp/both keep phone-key; new `EMAIL_RE`)
- `app/automation/broadcasts/page.js` (From-mailbox + signature pickers in the email block with auto-default + "Edit" link to Email settings + refetch-on-focus; rich body editor replaces the textarea; signature + HTML body rendered in the preview card; passes `emailAccountId`/`signatureId`/`bodyHtml` through preview + create; passes `channel` to AudiencePicker)
- `app/automation/broadcasts/RichEmailBodyEditor.jsx` (new — TipTap WYSIWYG for the email body: Insert-variable menu {{name}}/{{email}}/{{phone}}, bold/italic/underline/strike, color, align, lists, link, Cloudinary image insert, clear formatting; emits {html, text})
- `app/automation/broadcasts/AudiencePicker.jsx` (threads `channel` to the CSV importer: sends it in the upload, channel-aware hint text + invalid-row badge)
- `app/automation/broadcasts/BroadcastDetail.jsx` (channel-aware stats: email shows Total/Sent/Failed/Opens(—) + "delivery & open receipts aren't available over standard email" note; filters become All/Sent/Failed/Pending for email; invalid persisted filter falls back to All; recipient identifier + search + failed-CSV are email-aware)

What changed: email broadcasts previously sent via the legacy business-wide SMTP with a hardcoded "Powered by LeadForGrow" footer and no access to the per-mailbox `signatures[]`. Now a broadcast picks a Send-from mailbox + one of its saved signatures, sends from that mailbox's SMTP, and the signature is attached to every email — resolved ONCE per campaign (not per recipient) so a 5k send decrypts + renders once. The plain-textarea body is replaced by a rich WYSIWYG editor (same TipTap stack as the signature editor) with a personalization-variable inserter. The Broadcasts preview card now renders the real HTML body + signature + unsubscribe note ("aisa dikhega customer ko"). CSV import is channel-aware so email-only lists (no phone column) import by email. The broadcast detail's stat card was WhatsApp-shaped (sent→delivered→read from Meta webhooks) and showed a misleading "Delivered 0 / Read 0" for email, which has no delivery/read receipt over SMTP — email now honestly shows Sent vs Failed. Automation/sequences/tasks email paths are untouched (all new behavior isolated to the broadcast engine's account path, backward-compatible when no mailbox is selected).
Related decisions: preview uses the identical `resolveSignatureHtml` code path as the engine so the two cannot drift; `bodyHtml` kept separate from `body` (plain-text multipart + legacy fallback) so old broadcasts and other channels are unaffected.
Verification: production build compiled successfully (Redis ETIMEDOUT during build is the queue disabling itself offline, unrelated); full suite 543/543 tests pass. NOT viewed in a browser by me (the user is testing in their running dev server).
